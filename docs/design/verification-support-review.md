# Review: roadmap "Verification/Test Support"

Draft, 2026-11-15. This reviews the *Verification/Test Support* section of
`roadmap.md`, together with the neighbouring *fw-hdl-dv setup*, *Verification
IP* and *Registers* sections that it depends on. It also takes into account
`project-architecture.md` §3.2 (the `fw-dv` family), `core-protocol-kit-prep.md`
§9 and §11, and the testbench-to-testbed framing in `pitch.md`.

## 1. Summary

The section has the right core idea: *the design's structure and annotations
drive generation of the verification structure*. Its parts are sound:
- two entry levels (the design boundary, and a verification projection);
- an instrumented view that is generated by policy and costs nothing when
  it is off;
- shell and behavioural-model substitution;
- UVM interop as a first-class goal.

As a roadmap phase, though, it is a vision note. It has no deliverables, no
exit criteria and no sequencing, unlike the phases before it. Three things
are missing that the rest of the design set already depends on:
1. **Stimulus, checking and coverage aren't in it.** The section covers
   access and visibility only. The *Verification IP* section touches these,
   but only for kits.
2. **"Portable" is used once** ("checker portability") and never defined.
   Yet portability is the main reason to build this instead of using UVM or
   cocotb.
3. **Formal is absent.** The pitch still lists formal as weak with no
   mechanism (`pitch.md`, weak point 3). This section is where that
   mechanism would come from.

The biggest overlooked opportunity: **a testbench description that runs in
SV is a specification from which other implementations are derived.** Each
derived implementation may cover only a strict subset of the features. The
leading example is a host-side C++ implementation for emulation (§4.5).
It isn't a C++ *model* of the SV classes. It is a native, optimized
*implementation* of the same API (pooled transactions, built-in coverage,
on-demand logging) that the user calls directly. That mirrors how PSS
content is realized as target code. The same derivation also produces
formal and synthesized-testbed implementations. It also produces a **system
model for firmware development** (§4.6): the design's C model plus the
VIP as the rest of the system, driven by a Python harness, with firmware
and hardware events correlated on one timeline. The spec/implementation
split that fw-hdl already applies to design extends naturally to
verification content, and no competitor offers it.

## 3. Gaps

### 3.1 Structural gaps in the plan
- **G1. No deliverables or exit criteria.** Every earlier phase has them.
  Proposed phasing in §7.
- **G2. Three overlapping sections.** *fw-hdl-dv setup*, *Verification IP*
  and *Verification/Test Support* overlap, and *Registers* repeats the RAL
  and backdoor points. Merge them into one phase with sub-steps.
- **G3. No link to the repo plan.** `project-architecture.md` §3.2 already
  defines `fw-dv-spec`, `fw-dv-rt-sv`, a static/formal plugin, and
  per-kit `dv/` packages. The roadmap should place each item in one of
  those repos. Spec items need a **conformance suite**, as `fw-hdl-spec`
  has.
- **G4. "Verification library" vs "verification tooling" isn't kept
  apart.** The section mixes user-facing testbench content with
  implementation checks (cosim, equivalence). Architecture §3.2 keeps them
  apart, and this section should as well.

### 3.2 Missing verification functions
- **G5. Stimulus.** Not mentioned: sequences, scenarios, randomization,
  constraints. The *Verification IP* section asks "constraints in terms of
  the API?", and prep §11 Q9 leaves legality ownership open. Zuspec already
  models actions, constraints and coverage (PSS-like). That is the obvious
  portable home (§4).
- **G6. Checking and reference models.** Scoreboards aren't mentioned. The
  overlooked point: **the method-level model of the design is the reference
  model for every later refinement.** A generated scoreboard can run the
  class model and the lowered RTL side by side through the same API. The
  pieces exist (`verif/cosim`, `verif/canon` reorder-tolerant compare), but
  only as internal tooling, not as a user feature.
- **G7. Coverage.** Functional coverage over API transactions is
  mentioned only as "coverage monitors" under VIP. Structural coverage that
  the IR can provide is absent: FSM states and transitions, comb
  conditions, FIFO occupancy, arbiter grants.
- **G8. Assertions and properties.** The section mentions none. The
  *Verification IP* section has "property checkers written in terms of the
  API", with no temporal semantics.
- **G9. Test lifecycle.** There is no end-of-test, objection, timeout,
  reporting, error-count or pass/fail model. The domains work added a run
  lifecycle, so DV phasing should build on it, not invent a UVM-style
  phase set.
- **G10. Domains in checkers.** Every checker and coverage point needs a
  clock to sample on and a reset to disable it. These should come from the
  domain binding (core-domains), not be wired by hand. CDC analysis exists
  (crossing analysis) and is itself verification content; the section
  doesn't mention it.
- **G11. Test execution across implementations.** No plan for running the
  same test on the SV runtime, Verilator-lowered RTL, the C model and a
  testbed, or for how results are compared. dfm and pytest-dfm are the
  natural runner; the conformance-runner pattern is the model to copy.
- **G12. Debug output.** Transaction recording is mentioned, but no format
  is chosen. If recordings are to be compared across implementations (a
  cheap differential check), the format must not depend on the
  implementation.
- **G13. Mixed abstraction.** Shells are covered. Running part of the
  design as classes and part as lowered RTL in one sim (the normal state
  during refinement) is not.
- **G14. Python and cocotb.** Deferred in prep §10, and not mentioned
  here. For many open-source and FPGA users this is the first touchpoint.
- **G15. Synthesizable DV subset.** The pitch's testbed framing needs a
  published subset (fixed structure, no allocation after time 0, bounded
  queues). The section only says "fast emulation environments (typically
  C++)". This subset is also what formal needs (§5), so one definition
  serves both.

## 4. Portable content

### 4.1 What "portable" should mean
**Definition.** Portable doesn't mean "the same source runs unchanged
everywhere". It means **the SV description is the specification, and
other implementations are *derived* from it.** Each derived implementation
states the feature subset it supports, and it must conform to the SV
behavior within that subset. This is the PSS model:
- a PSS description is realized as C on an embedded core, as SV in a
  testbench, or as a test file;
- each realization is native code, not an interpreter of the model;
- the description stays the single source.

Here the SV runtime plays the role of the reference realization. Derived
realizations (host C++, synthesized RTL, formal harness) are generated
through Zuspec IR. The "C++" in the tables below always means a derived
native implementation, not a C++ model of SV semantics.

Each axis below is a separate claim:

| Axis | Portable across | Mechanism already planned |
|---|---|---|
| Implementation | SV runtime, other simulators' native runtimes, **derived native implementations** (host C++, C model) | spec/impl split, conformance, Zuspec back ends (`zuspec-be-sw`) |
| Abstraction | method model → sync RTL → gates | API plus transactors (prep) |
| Engine | simulation, formal, FPGA/emulation testbed, C++ | Zuspec IR plus engine back ends |
| Language/framework | SV classes, UVM, Python/cocotb | generated bindings (pyhdl-if), UVM shells |
| Project | reuse across designs and teams | kits' `dv/` packages, `fw-dv-spec` std library |
| Tool | commercial tools that never see fw-hdl | emitted plain SV / SVA / bind modules ("build with fw-hdl, ship plain SV") |

### 4.2 Content that can be portable, and what it gains

| Content | Written once as | Rendered to | Benefit |
|---|---|---|---|
| **Protocol rules / checkers** | rules over API events (the listener contract, prep §4.3) | SV class checker; bind module with SVA; synthesizable checker for FPGA; C++; formal assertion | One rule set checks sim, the board and proofs. The kit author doesn't maintain three copies that drift apart. Plain SVA output reaches users of commercial tools. |
| **Legality constraints** | Zuspec constraints on the txn fields of a request or response | `randomize()` constraints; Python solver; host-side descriptor generation for the testbed; **formal assumptions** | The same text is stimulus *and* environment model. This is the strongest single dual-use item; see §5.2. |
| **Coverage model** | coverpoints and crosses over API txns, plus IR-derived structural points | covergroups; Python coverage; synthesizable counters; formal `cover` | Coverage closure is measured the same way in sim, on the board and in formal. Formal cover finds unreachable bins early. |
| **Scenarios / sequences** | Zuspec actions (PSS-like) | SV sequences; Python; host-side scenario driver for the testbed | Tests move from sim to the board unchanged. Aligns with Accellera PSS, which buyers already know. |
| **Reference model** | the design's own method-level class model | scoreboard input in sim; C++ model; formal equivalence target | No separate golden model to write. This is unique to a class-first flow. |
| **Scoreboards / comparators** | std-library components in `fw-dv-spec` (in-order, reorder-tolerant from `verif/canon`) | every implementation | Standard comparison semantics; less bespoke testbench code. |
| **Register model** | the register spec (*Registers* section) | RAL (SV, Python); C header/driver; UVM `uvm_reg` adapter; backdoor on every abstraction; generated reset-value and access-policy properties | One spec feeds design, DV, firmware and formal. The backdoor works without VPI. |
| **Tests** | method-level tests against the API | every abstraction and every implementation | The pitch's headline ("designer tests an order of magnitude better") depends on this. |
| **TB structure** | generated from the elaborated IR | plain-SV top; UVM env shell; cocotb harness | Users of other frameworks get value without adopting fw-dv. |
| **Recordings** | implementation-neutral txn stream | waveform viewers; diff between implementations | Cheap differential check between abstraction levels, and one debug format. |

### 4.3 Why it matters
- **Cost.** Today a protocol's checker, coverage and stimulus are written
  separately for UVM, SVA/formal, cocotb and emulation. These copies drift
  apart, and that drift is a known source of escapes. Writing once removes
  the multiplier.
- **Trust in refinement.** If the same checks run at every abstraction,
  equivalence is checked continuously, not just asserted. This answers the
  pitch's weak point 6.
- **Market reach.** Plain SV/SVA and UVM output let kits sell to teams that
  never adopt fw-hdl. That is the *Featherweight family* strategy (IP is the
  flagship; ship plain SV) applied to VIP.
- **Differentiation.** UVM can't render to formal or hardware. cocotb can't
  render to anything but simulation. Emulator vendors' behavioural compilers
  are tied to one emulator. Portability across engines is the defensible
  part.

### 4.4 Constraint that portability imposes
Derivation needs the content in Zuspec IR, so it must be analyzable.
That doesn't mean declarative only. Procedural SV in testbench classes
(sequences, scoreboards, reference models) can be translated, just as
design classes are. What portability imposes is a set of **published
subsets, one per derived implementation**:

| Subset | Allows | Excludes |
|---|---|---|
| Full SV | everything | nothing (reference realization) |
| Host-native (C++) | procedural code, dynamic objects (pooled), blocking calls (mapped to coroutines), `randomize()` (runtime solver), user-supplied native functions | timing outside the HW channel (`#delay`, `@(signal)`), VPI, constructs whose type is resolved at run time when the factory is closed at elaboration |
| Hardware (synth testbed, formal) | fixed structure, bounded state, LFSR or host-supplied randomness | allocation after time 0, unbounded queues, solver |

Each construct in `fw-dv-spec` is tagged with the subsets that support
it. A class is checked against the subset it is meant for, and fails at
generation time, not at run time. Decide the tags early: retrofitting
them is expensive.

### 4.5 Host-side C++ for emulation and acceleration

**The problem.** In transaction-based acceleration, the host side of the
testbench is usually the bottleneck. An SV testbench running in a
simulator coupled to the emulator runs at simulator speed. Teams therefore
rewrite the host side in C/C++ by hand. That second copy is debugged
separately and drifts from the simulation testbench.

**The proposal.** Derive the host side from the SV testbench:
- The path is SV DV classes → `fw-hdl-fe-sv` → Zuspec IR → a Zuspec
  software back end. `zuspec-be-sw` already compiles Zuspec components to
  C, and PSS actions, activities and constraints to C. Its PSS path
  includes runtime solving (dv-solve, through `zuspec-solver`) and a
  scheduler (`zsp_timebase`). This is the route, not new emission code in
  fw-hdl.
- The output is a library with the same method API as the SV classes:
  transaction types, sockets, sequences, checkers, coverage. **The user
  calls it** from their own C++ test, from Python through bindings, or
  from a PSS-generated scenario. It doesn't simulate SV; it is the
  implementation.
- The partition is the one in the pitch's testbed framing. The factory
  places transactors and per-cycle work in hardware. The method
  interfaces that cross the boundary become generated channels. The host
  side of those channels is now native C++ instead of SV in a simulator.

**Where the speed comes from.** All of these are possible because
structure is fixed at elaboration, so the generator knows the whole
testbench:
- *Devirtualization.* Factory overrides are resolved before generation,
  so dispatch can be static, and calls can be inlined across API calls.
- *Memory pools.* Transaction classes get per-type pools or arenas.
  Their lifetimes can often be bounded from the listener fan-out (who
  holds a handle), so objects are recycled without GC or refcounting in
  the common case.
- *Wire-compatible layout.* Txn structs use the same packed layout as the
  generated channel, so sending one is a copy into a batch buffer (or no
  copy), not a marshalling step.
- *Batching.* Calls that cross the channel are batched and streamed, and
  only block when the API's semantics require a response. Never stall per
  transaction (SCE-MI pipes and FireSim bridges solve the same problem).
- *Compiled-in coverage.* Coverpoints become counter arrays updated
  inline. Crosses that are known statically become flat indexing. Results
  are merged into the same coverage database format as simulation.
- *On-demand logging.* Log and recording sites are compiled in, but
  gated by a cheap runtime check. A flight-recorder mode keeps the last N
  transactions per port in a ring buffer and dumps them only when a check
  fails. That is the debug model that works at emulation speed.
- *Concurrency.* Sequences and blocking calls become stackless
  coroutines on one scheduler. Independent agents can be spread across
  host threads when they share no state, which the IR can check.
- *Randomization.* Use dv-solve, the fast solver we already have.
  `zuspec-solver` turns each constraint set into a relocatable dv-solve
  problem blob at generation time, so the host only binds values and
  solves. Add LFSR fast paths for unconstrained fields, and precomputed
  tables for small domains where that pays.

**What else it enables:**
- *Verilator.* The same C++ links directly into a Verilator binary. Tests
  run at C++ speed, with no DPI layer and no SV class runtime.
- *Pure software.* Host C++ linked against the design's C model (also
  derived through Zuspec) gives a fully software regression with no
  simulator.
- *FPGA testbed.* The host side runs on the board's Arm cores or a PC
  (`fpga-system-stimulus.md`, scenario layer). Today that layer is
  planned as Python; native C++ removes the throughput limit.
- *Product.* A shipped VIP (a kit's `dv/` package) carries its host
  implementation. A team on an emulator gets fast host-side VIP without
  adopting fw-hdl, the same "build with fw-hdl, ship plain SV" principle
  applied to C++.

**How it stays correct:**
- The derived implementation runs the `fw-dv-spec` conformance suite for
  its subset.
- Differential runs: the same scenario and seed on the SV runtime and on
  host C++, against the same design model. Compare the
  implementation-neutral recordings (§4.2), allowing reordering where the
  spec allows it.
- *One solver everywhere.* If the SV runtime can also call dv-solve
  (through DPI, as an optional realization of `randomize()` for
  `fw-dv` classes), the same seed gives the same values on every
  implementation. Differential runs then compare exactly, not "same legal
  set". A failure seen on the emulator can be reproduced in simulation
  from the seed alone. The native simulator solver stays available; the
  dv-solve path is what makes cross-implementation runs reproducible.
- User-supplied native code (the PSS "foreign function" equivalent) is
  declared in the SV source as an import with a contract. It is the only
  place where the host implementation can diverge from SV, and it is
  marked as such.

### 4.6 System model for firmware development

**The need.** Low-level firmware (boot, bring-up, management-core
firmware, link and PHY management) is developed against a fast C model of
the hardware. The model alone isn't enough, because the firmware reacts to
the rest of the system. A test of link training, for example, is an
interleaving of:
- software-like prompts to firmware on the management core, such as
  mailbox commands ("bring up port 2 at Gen4");
- hardware behavior the firmware must react to: the link partner's
  training sequences, a timeout, a speed downgrade, an injected error at
  a particular stage;
- checks on both sides: the firmware's replies and the hardware's state.

When such a test fails, the question is always *"what was the firmware
doing when the link was in state X?"* Without correlation, firmware and
hardware logs are two unrelated streams, and debug is guesswork.

**Why it falls out of this plan.** Almost every part of the system model
is a derived implementation of something that already exists for
verification:

| System-model part | Derived from |
|---|---|
| Fast C model of the design | design classes → Zuspec → `zuspec-be-sw` (already planned) |
| Rest-of-system models (link partner, host, memory, sensors) | the same VIP used in sim: kit transactors' class side and behavioral peers, as host-native C++ (§4.5) |
| Event injection ("fail at Polling.Compliance") | the impairment layer (`fpga-system-stimulus.md`) and scriptable deviations in partner models |
| Firmware's view of hardware | the register model: generated C header/HAL for firmware, the same spec as the RAL (*Registers*) |
| Harness control of hardware state | RAL backdoor, which works on every abstraction |
| Scenario | Python harness over generated bindings; or Zuspec activities (PSS-like) where scenarios should be portable and solvable |
| Recordings | the implementation-neutral transaction stream (§4.2) |

**The Python harness.**
- Python calls the derived C++ APIs through generated bindings (the
  pyhdl-if work deferred in prep §10 becomes a dependency here).
- It is written as `async` code. It awaits *system events*, not clock
  edges: `await link.stage("Polling")`, `await fw.mailbox.reply()`,
  `await fw.log_matches("speed change")`.
- It can send firmware prompts and inject hardware events in one
  scenario, with ordering expressed relative to observed stages.
- The same scenario API should run against:
  - the system model (fast C, firmware host-compiled or on an ISS);
  - RTL simulation with the management core in RTL or as an ISS;
  - emulation, with the host side from §4.5;
  - the board, where the harness reaches the mailbox through a debug
    probe or host interface.

  Firmware tests then follow the hardware down the abstraction ladder, as
  designer tests do. They also become **post-silicon bring-up scripts**
  with no rewrite.

**Correlation: the critical feature.**
- *Observable stages.* Components declare their high-level state as an
  observable: LTSSM state, mailbox state, DMA ring state. The generator
  records every change as an event. A protocol kit can ship the stage
  model for its protocol, so the observable comes for free with the VIP.
- *One timeline.* Firmware events, model events and harness actions all
  go into one trace, with one timebase:
  - firmware events: log calls, function entry and exit (from the ISS or
    compiler instrumentation), and every MMIO access;
  - model events: stage changes, transactions, injected faults;
  - harness events: prompts and their replies.
- *Decoded register accesses.* Every MMIO access is decoded by the
  register model into register and field names ("wrote
  `LINK_CTRL.target_speed = GEN4`"). Raw addresses are hidden. This one
  feature is often enough to explain a firmware/hardware mismatch.
- *Causality.* Record which firmware access triggered a model reaction,
  and which model event raised the interrupt the firmware handled. A
  viewer can then walk the chain backwards from a failure.
- *Same trace on every platform.* The format is the implementation-neutral
  recording from §4.2, so a trace from the board and one from the model
  can be compared side by side.
- *Flight recorder.* As in §4.5, keep full detail in ring buffers and dump
  on failure, so the system model stays fast.

**Firmware execution options.**
- *Host-compiled against the generated HAL.* Fastest, good for logic
  bugs, needs the HAL to hide MMIO behind generated accessors.
- *On an ISS* (Spike, QEMU or similar) with MMIO callbacks into the C
  model. Runs the real binary, catches compiler and ABI issues, and is
  slower.

  The generated register-access layer should make both work from one
  firmware source.

**Determinism.** Firmware tests on the system model must be replayable:
seeded randomness (dv-solve, §4.5), a harness-controlled time model, and
recorded harness inputs. Then a failure found in a nightly run is
reproduced exactly in a debugger.

**Benefits.**
- Firmware development starts before RTL, against a model derived from the
  same source as the hardware, so it can't drift from the RTL.
- The rest of the system costs little to build: it is the verification
  IP, reused.
- One scenario suite covers the system model, RTL, emulation and the
  board.
- Correlated, register-decoded traces cut the most expensive debug loop
  in bring-up: firmware and hardware teams arguing over two
  uncorrelated logs.
- It extends the Registers phase's "one spec" claim to firmware.

## 5. Formal (not yet addressed)

### 5.1 Why formal belongs in this phase, not after it
Most formal value comes from content this phase defines anyway: the
checkers, constraints, coverage and reference model in §4.2. Designing that
content sim-only and adding formal later would cause the drift that
portability is meant to prevent. The repo already has the pieces
(`formal/lift`, `prove`, `replay`, `codegen_equiv`, the sync-lowering
equivalence proofs, and SBY components in kits). The roadmap doesn't
mention any of them.

### 5.2 Opportunities
- **F1. Assume-guarantee from protocol kits.** For a port in role R, the
  kit's legality constraints become *assumptions* on inputs, and its rules
  become *assertions* on outputs. The roles swap exactly as transactor roles
  do (prep §9). Every wrapped IP with declared protocol ports then gets a
  formal harness generated with no user effort. The demo "wrap your RTL,
  get a formal testbench" is cheap, and it addresses the verification-first
  audience directly.
- **F2. Std-library contracts as properties.** `fw_fifo`, arbiters, credit
  counters and the rest ship contract properties (no overflow or
  underflow, ordering, fairness). Principle 5 of project-architecture
  already requires native realizations to be "checked against the class's
  contract". Formal contracts are the mechanism that makes that rule
  enforceable. They also become conformance evidence.
- **F3. Free design checks from the IR.** Some checks need no properties
  from the user: the single-writer rule (*Basic RTL*), comb-loop absence,
  reset completeness (every state element reset or declared don't-care),
  X-propagation from uninitialized state, and domain crossings (the
  existing crossing analysis, made a reported check).
- **F4. Equivalence across refinement.** Prove that the class model and the
  lowered RTL are equivalent (this exists for sync lowering). Expose it as a
  user-facing check for the user's own refinements, with the
  method-level model as the spec.
- **F5. Formal SVUnit / test lifting.** A directed method-level test lifted
  to a bounded proof by symbolic inputs (`formal/lift`). Counterexamples
  are replayed as sim tests (`replay`). This bridges designers' tests to
  formal with no new language, and it fits the "designer tests" headline.
- **F6. Cover as a coverage engine.** Coverage bins (§4.2) become formal
  covers. Unreachable bins are found up front, and witness traces seed
  directed sim tests.
- **F7. Method-level formal before RTL.** Properties on the API can be
  checked on the class model (through the IR) before any RTL exists.
  Then the same properties are re-checked through transactors on the RTL.

### 5.3 Formal-specific decisions to make
- **Property language.** Options:
  (a) SVA text, which reaches only SV tools and can't be analyzed by Zuspec;
  (b) observer components: synthesizable class monitors that flag
      violations, which render everywhere but express liveness awkwardly;
  (c) a small temporal property layer in Zuspec IR that emits SVA and also
      lowers to observers.

  **Recommendation: (c), starting with (b) for safety properties.** Add
  bounded "eventually" and fairness primitives for ready/valid liveness
  later.
- **Engine route.** Emit SVA plus a harness for stock tools (SBY,
  commercial) through `dv-flow-libformal`, *and* allow native solving on
  Zuspec IR. Neither may be the privileged path (same rule as XLS: a peer
  behind an engine interface).
- **Environment from domains.** Clock relations, the reset sequence and
  the reset-assert assumption should be generated from the domain binding.
  Hand-written formal setup is where most false failures come from.
- **Abstraction and bounds.** Large memories and deep FIFOs need
  abstractions (free memories, counter abstraction). Std-library components
  could ship formal-friendly abstract realizations: a third realization
  next to the portable SV and the native one, held to the same contract.
- **Shared subset with the testbed.** Formal monitors and the synthesizable
  testbed need the same bounded, static subset (G15). Define it once.

## 6. Open issues

1. What is the "verification projection"? A generated set of classes (as
   the *fw-hdl-dv setup* section leans), runtime reflection through the
   visitor API, or both? Recommendation: generated, with the visitor as
   the spec-level primitive the generator and tools use.
2. Who owns legality constraints: the kit or the user (prep §13 Q9)? With
   F1, the kit must own a *legal* constraint set, because it becomes the
   formal assumption. Users add test-specific constraints on top.
3. Is Zuspec's action/constraint model the fw-dv stimulus language, or does
   fw-dv define its own and lower to Zuspec? AGENTS.md ("prefer
   representing it in Zuspec") points to the former.
4. Which direction does UVM interop run, and in what order: fw-dv content
   inside a UVM env, or UVM VIP inside a generated env?
5. What is the randomization equivalence criterion across implementations?
   The pitch says "same legal set, not same values". With dv-solve on
   every software implementation (§4.5), exact seed reproducibility
   becomes achievable. Is it a goal, and does it extend to hardware
   randomness (LFSR) on the testbed?
6. What is the instrumentation cost model in lowered RTL? Is the "ports as
   monitors" view available on RTL only through bind, or also as
   generated taps?
7. Where does the traceability map (RTL name → class path / API event)
   live, and which tool consumes it (waveform viewers, formal CEX display,
   replay)?
8. How does the conformance suite cover `fw-dv-spec`? It needs
   minimum-bar semantics for checkers and coverage sampling, like the
   design suite.
9. When do the existing internal tools (`verif/cosim`, `verif/canon`,
   `formal/*`) become user features, and where do they move per
   architecture §3.3?
10. Where does the host-native subset's boundary sit? In particular:
    what time model the host has (only the channel's synchronization
    points?), and how user-supplied native functions declare their
    contracts.
11. What is the channel ABI: our own, SCE-MI 2 pipes, or vendor APIs
    behind a pluggable transport? The generated host side should not
    depend on one emulator.
12. Does the PSS → C path in `zuspec-be-sw` and the SV-testbench → C++
    path share one scenario runtime? They should, so that PSS scenarios
    can call derived fw-dv APIs directly.
13. How does firmware run in the system model: host-compiled against a
    HAL, on an ISS, or both? Both, probably, but the register model's
    generated access layer must hide the difference (§4.6).
14. How are the system model's time and the firmware's time kept
    together (lockstep, quanta, or event-driven sync at MMIO accesses),
    and is the result deterministic enough to replay?
15. How does a component declare its observable stages (for example
    LTSSM state) so the generator can expose and record them? Is this a
    protocol-kit API feature, a coverage feature, or its own annotation?
16. What is the system-trace format, and the viewer? It must merge
    firmware, model and harness events on one timeline.
17. Where does the system-model layer live: `fw-dv`, a new repo, or the
    Zuspec org next to `zuspec-be-sw`?

## 7. Suggested restructuring of the roadmap phase

Merge the three DV sections into one phase with these steps, each with exit
criteria:

| Step | Content | Exit criterion |
|---|---|---|
| V0 Observation | visitor API (spec), listener contract, bind monitors, path-reachable sockets (mostly prep) | prep §9 acceptance: wrap_rtl in Verilator, cycle-matched |
| V1 Portable test core | `fw-dv-spec` skeleton; run lifecycle; method-level tests running on class model and lowered RTL; class-model-as-reference scoreboard; implementation-neutral recordings | one test, two abstractions, auto scoreboard, same recording |
| V2 Portable content | rules, constraints, coverage as Zuspec IR; SV and SVA renderings; rv kit `dv/` | rv rules render to a class checker *and* a bind/SVA checker that agree on a fault-injected trace |
| V3 Formal | F1 assume-guarantee harness, F2 std-lib contracts, F3 free checks, through SBY plus a Zuspec native route | wrapped rv IP gets a generated formal harness that passes, and a mutated IP fails with a replayable CEX |
| V4 Interop | UVM env and agent shells; pyhdl-if/cocotb bindings | an existing UVM test uses a generated agent; a cocotb test drives the method API |
| V5 Host-native | host-native subset tags; SV DV → Zuspec → `zuspec-be-sw` C++; pools, compiled coverage, flight-recorder logging; dv-solve randomization; Verilator link | the same rv test runs on the SV runtime and as linked C++ in Verilator, with identical recordings from one seed, and a measured speed-up |
| V6 Testbed | synthesizable DV subset; checkers and coverage synthesized; generated channel to the V5 host side | traffic-generator demo checked on FPGA with the same rules as in sim, host side in derived C++ |
| V7 System model | design C model plus host-native VIP as the rest of the system; generated firmware HAL; Python `async` harness over bindings; observable stages; a single correlated, register-decoded trace | a mailbox-driven firmware test of a link-training-style flow, with an injected fault at a chosen stage, runs on the system model and in RTL sim from one scenario, and produces a correlated trace that shows the firmware's response to each stage |
| Registers | as written, plus generated register properties (V3) and C header | backdoor works on class and RTL; reset-value properties prove |

Put V3 before V4 and V5. It reuses V2's content directly, it costs little
given the existing `formal/*` code, and it gives the pitch the formal
mechanism it lacks.
