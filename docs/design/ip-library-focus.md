# Focus for the IP library: lift, prove, model

**Current direction (2026-11-15, the user's refinement):**
1. Collect open-source IP that is already used in RISC-V systems.
2. *Lift* it into higher-abstraction fw-hdl.
3. Prove the lifted design equivalent to the original.
4. Produce fast software models from the lifted source.

§0 sets this out. Sections 1–4 still hold as the case for software-visible
platform IP. Section 0's sequence replaces §5. The block inventory is in
`research/riscv-ip-inventory.md`. The automated, DV-grounded lifting
process, including operation-level equivalence for lifts that are not
cycle-exact, is in `automated-lifting.md`.

Draft, 2026-11-15. The supporting research is in `research/ip-market.md`.
This note extends `featherweight-ip-strategy.md` §3 (P1 and P4) and step 5 of
the path in `wedge-assessment.md` §4b.

**Question.** Wrapped OpenCores/freecores IP gives proof points and examples.
Is there a category of IP worth designing *from scratch* that plays to
fw-hdl's strengths: several abstraction levels from one source, programmatic
configuration at elaboration, and a model fast enough for software emulation
(QEMU, Renode)?

**Recommendation.** Focus on **a software-ready RISC-V platform kit**: the
platform IP that an operating system talks to. Build it so that one
configuration produces:
- the RTL;
- the device behaviour models for QEMU and Renode;
- the device tree and headers;
- the tests.

Lead with the platform interrupt controllers, then a virtio device family,
then the RISC-V IOMMU. The cores, interconnect and simple peripherals are
wrapped or reused, not written.

## 0. Lift, prove, model

**The argument.** The need for software models is what makes lifting worth
doing. A fast model from the same source as the RTL can only come from a
description above RTL. Writing that description from scratch throws away
IP that people already trust. Lifting keeps the trust: an equivalence proof
says the lifted design *is* the IP you already use. The model then comes
from it for free.

**Why it is stronger than from-scratch:**
- **Instant credibility.** "Here is the OpenTitan UART you already use,
  proven equivalent, now with a fast model" needs no argument about QoR or
  verification quality. The original's silicon history and DV carry over.
- **Upstream DV is reusable.** OpenTitan's UVM benches and PULP's
  testbenches can run against the lowered RTL as a second check.
- **There is a comparison to beat.** lowRISC's hand-written QEMU models grade
  themselves from "near feature-complete" to "dummy". A lifted model has full
  coverage by construction, and the gap can be measured.
- **It absorbs the freecores work.** The P2 core rewrites (16550, I2C,
  picorv32, wb-dma, each verified against a reference) are already lifts.
  They become the first entries of the series, now with equivalence and
  models as the published result.
- **Drift detection becomes a product.** Re-running equivalence on each
  upstream release flags exactly what changed. That is stronger than
  OpenTitan's `checkregs.py`, which checks register addresses only.

**The equivalence chain.**

```
 original RTL  ==SEC==  lifted design, lowered to RTL
                              |  same source
                              v
                        fast model (register-accurate, untimed)
```

- **First link: sequential equivalence (SEC) between the original RTL and
  the lowered lift.** This is a full proof when the lift keeps the
  original's cycle behaviour.
- **Second link: the fast model is the lifted design's function without its
  timing.** It is right by construction, provided fw-hdl keeps them apart in
  the source, backed by the conformance suite and by bounded formal checks
  on register-level behaviour.

**Lift levels.** Each block declares which level it reached:

| Level | Lift | Equivalence | Model |
|---|---|---|---|
| L0 | Wrapped only | — | None. Co-simulate the RTL |
| L1 | Cycle-accurate, RTL-subset fw-hdl, with registers and transactions made explicit | Full SEC against the original | Generated by abstracting the timing |
| L2 | Transaction-level (SPL or higher); the microarchitecture may differ | At transaction boundaries: refinement checking, plus upstream DV on the lowered RTL | Generated directly |

L1 is the default. Use L2 only where the higher level pays for itself, such
as DMA engines or the IOMMU.

**The architectural requirement this puts on fw-hdl.** The lifted
description must separate a block's *function* (register semantics and what
each transaction does) from its *timing* (the cycle-level
microarchitecture). Without that separation, the "fast model" is just the
RTL compiled to C, and Verilator already does that. Make the claim
measurable:
- The model boots Linux at QEMU-class speed, with **at least 100x
  Verilator's speed on the original RTL** as the bar.
- It is register- and interrupt-accurate, not cycle-accurate.

**"Prove, don't replace" as the first release.** A user can keep the upstream
RTL and take only the generated model and the equivalence proof. This is
additive and has no friction, in the same pattern as the observability kit
(`wedge-assessment.md` §4b). Shipping the lifted RTL comes later and is
optional.

**What it costs and needs.**
- **Lifting effort is the scaling limit.** The equivalence checker makes
  assisted lifting safe: an LLM, or a script that turns reggen/hjson into
  register classes, proposes the lift, and SEC accepts or rejects it. Wire
  the register-generator inputs (hjson, SystemRDL) in directly, so the
  register layer is never lifted by hand.
- **SEC tooling.**
  - Open: yosys `eqy`, which needs state matching (fine for L1), and
    SymbiYosys for bounded checks.
  - Commercial: Jasper SEC, VC Formal SEQ, Questa SLEC.
  - Publish proofs that run on the open tools.
- **Hard cases** need L2 or stay wrapped:
  - clock-domain crossings;
  - asynchronous resets;
  - generated or encrypted primitives;
  - analog.
- **Licences carry over.** OpenTitan is Apache-2.0, PULP is SHL-0.51 and
  freecores is often LGPL. Apache-2.0 cannot be combined with GPLv2-only
  QEMU. So:
  - target **Renode (MIT) first**;
  - reach QEMU out of process (vfio-user or remote-port), or only for
    GPL-compatible sources.

**Assembly completes the story.** Lifted IP gives each block an RTL and a
model from one source. Assembly does the same for the whole system. The
platform configuration that instantiates and connects the lifted blocks
produces, from the same source:
- the RTL SoC;
- a full emulation platform: the Renode or QEMU machine with every device's
  generated model wired at the same addresses and interrupts;
- the device tree and headers;
- the tests.

Existing tools generate only the platform wiring (LiteX's Renode
generator) or a machine skeleton (OpenTitan's `autotop.py`), and fill in
device behaviour by hand. Here, assembly *plus* lifted devices yields an
emulation platform that is complete and matches the RTL by construction.
**Assembly is the headline; lifting is what makes it true.**

**Lifting existing IP and refining new IP use the same mechanism.** Lifting
goes up from existing RTL. New design goes *down*: a designer writes the
design view at a high level, gets the fast platform from it at once, then
refines toward RTL, with equivalence (or transaction-level refinement)
established at each step. Teams are already under pressure to deliver fast
platforms (virtual prototypes for shift-left software), and today a
separate modelling team writes them and they drift from the RTL. Deriving
the platform from the design view gives designers a reason to adopt fw-hdl
that isn't about RTL productivity: **the platform the software team needs
falls out of the design work instead of being a second project.**
- The early design view needn't be the final one. It is a legitimate
  deliverable as soon as the register map and function are settled.
- Refinement keeps it honest. Once the RTL is refined, the platform is
  still the same source, proven equivalent, not a model that was right in
  month 2 and wrong by tapeout.
- Lifting proves the mechanism on IP people already trust. Refinement is
  how a team uses it on their own new blocks. The case studies
  (Cheshire, lifted) are the evidence for the design-side pitch.

This needs the function/timing separation above, plus a refinement check
between levels (L2 to L1) as well as SEC at L1. See risk 1 in §6 on the C
view.

**Target platform: Cheshire.** It is a Linux-capable PULP SoC on CVA6. Its
IP mixes PULP, OpenTitan (Apache-2.0) and CVA6 blocks. **The inventory
confirmed that neither upstream QEMU nor Renode has a Cheshire machine.**
Most of its devices already have stock models elsewhere (16550, CLINT,
PLIC), so a generated machine can be cross-checked device by device. The
gaps (the OT i2c, spi_host and gpio, axi_vga, iDMA) are where generated
models are new.

That gives a concrete headline: **"Cheshire, lifted"**. A generated
emulation platform for a real taped-out Linux SoC, with every device proven
equivalent to the RTL that was taped out.

Caveats from the inventory:
- Cheshire's Linux support is out of tree (a CVA6-SDK fork with an
  OpenTitan spi_host driver).
- Cheshire has no AIA.
- The OpenTitan peripherals in Cheshire are PULP ports: TL-UL is replaced
  with regbus and the countermeasures are stripped. Reusing OpenTitan UVM
  needs a shim.

**Revised sequence.** This replaces §5.

| Step | Deliverable | Exit test |
|---|---|---|
| 1. Pilot | Lift Cheshire's `obi_uart` (SHL-0.51, 1.26k lines, 16550-compatible). L1, SEC against the original, generated Renode model. Its LGPL predecessor shipped a Formality VHDL-vs-SV equivalence script, which is precedent. The freecores 16550 rewrite is the practice run; it is LGPL, so it is not the release target | Proof passes in the open tools. The same Linux image gets a console on Renode (generated model) and on Verilator (original RTL). Report model speed and the lift's line count |
| 2. Timer and interrupts | pulp `clint` (459 lines, PeakRDL) and rv_plic in Cheshire's configuration (mostly reggen output); OT `rv_timer` to prove the reggen-to-register-class path. L1 | Same, plus the upstream Linux drivers working unmodified |
| 3. OpenTitan peripherals | gpio and spi_host (in Cheshire), the OT uart, then i2c (filters, clock stretching). OT UVM needs a TL-UL-to-regbus shim, or lift the upstream TL-UL versions | Coverage compared against lowRISC's QEMU grades; OpenTitan DV passing on the lowered RTL |
| 4. Platform machine | A generated Renode `.repl` (then QEMU) for Cheshire. Neither upstream QEMU nor Renode has a Cheshire machine | Linux boots on the generated machine |
| 5. AIA | Lift zero-day-labs riscv-aia (APLIC first) and add it to the Cheshire configuration (Cheshire has no AIA today), with formal properties | Equivalence plus the first formal proofs of open AIA RTL |
| 6. DMA and IOMMU | iDMA and the IOMMU at L2 | Transaction-level equivalence; the IOMMU checked against the spec's C reference model |
| Exception | Virtio: nothing to lift, so build it new on the shared ring engine | Later |

## 1. The gap

From the research:

1. **Every SoC that runs software needs these devices modelled.** QEMU,
   Renode, VCML and Linux converge on one set:
   - 16550 and PL011 UARTs;
   - PLIC, ACLINT and AIA interrupt controllers;
   - the RISC-V IOMMU;
   - virtio;
   - SDHCI, AHCI, NVMe and xHCI storage and USB controllers;
   - PL330 DMA.
2. **Open RTL for these devices is thin.**
   - The 16550 survives only in OpenCores-era repos.
   - AIA and IOMMU RTL each come from one group and say "not formally
     verified".
   - Open virtio RTL is close to non-existent.
   - There is no open AHCI, xHCI or e1000.
3. **Models are written by hand and drift from the RTL.**
   - OpenTitan's QEMU fork pins to an old RTL tag and grades its devices from
     "near feature-complete" to "dummy".
   - It also built tools to check register addresses (not bits) and to
     generate device skeletons.
   - LiteX's Renode generator special-cases every place the models lag the
     RTL.
4. **Nobody generates peripheral behaviour models from the RTL source.**
   - LiteX generates the Renode *platform*, but not the behaviour of its
     peripherals.
   - Chipyard runs one image on QEMU and FireSim, but its devices are written
     twice.
   - Codasip does single-source models only for processors.

Point 4 is the opening. The fw-hdl claim lands exactly here: one class
description runs as the fast model and lowers to the RTL. A configuration
object drives the RTL, the model, the register map and the device tree
together. The claim is checkable: the same unmodified Linux image and upstream
driver boot on QEMU, on Verilator and on an FPGA.

## 2. Candidates considered

| Category | Software model value | Fit with configuration and abstraction | Open competition | A small team can do it | Verdict |
|---|---|---|---|---|---|
| **RISC-V platform interrupt kit** (PLIC, ACLINT, APLIC, IMSIC) | High: Linux drivers, QEMU and VCML models exist to test against | High: sources, harts, guest files, direct vs MSI mode, domains | One unverified AIA repo; PLIC/CLINT only inside generators | Yes: small datapath, formal is tractable | **Lead** |
| **Virtio-mmio family** (console, rng, blk, net) on one virtqueue engine | High: one image runs on QEMU `virt`, Renode and FPGA | High: one transport, swappable device back-ends | Essentially none | Yes, staged | **Second** |
| **RISC-V IOMMU** | Highest: hypervisor and VFIO bring-up | High: staged feature sets | One unverified repo; the C reference model in the spec repo is a ready oracle | Hard: page walks, IOTLB, queues | **Third, staged** |
| **Platform generator** (configuration to RTL top, QEMU/Renode machine, device tree, headers) | Multiplies everything above | It *is* elaboration-time configuration | LiteX, Chipyard, topgen | Yes, once devices exist | **The frame**, built alongside |
| Driver-compatible basics (16550, PL011, SDHCI, PL330-like DMA) | Medium: upstream drivers exist | Low novelty | Old or missing | Yes | **Filler and pilot**; the 16550 is the pilot |
| Interconnect / NoC generator | Low for QEMU (software doesn't see it); high as a performance model | Very high | PULP axi is strong | Medium (deadlock, ordering) | **Enabling layer**; wrap or reuse first |
| DMA engine family | Medium (software-visible) | Very high (cf. iDMA) | iDMA is strong and open | Yes | Later; complement iDMA rather than rewrite it |
| xHCI, AHCI, NVMe device-side controllers | High | Medium | None | No: large, with a PHY dependency | Defer |
| CPU cores, PHYs, GIC | — | — | Crowded, needs silicon, or needs an Arm licence | No | Avoid |

**Why not lead with interconnect or DMA?** Those are the strongest pure
configuration plays, and Arteris and Baya show they make money. But software
doesn't see an interconnect, so the QEMU benefit is nil. The open incumbents
(PULP axi, iDMA) are also good. The interconnect is still needed: wrap PULP axi
or build a modest crossbar generator on `fw-proto-axi`. Return to a modelled
NoC as a separate product once the platform kit has credibility. The "model
before RTL" pitch is Baya's, and it fits fw-hdl.

**Why not "an SoC" in general?** An SoC kit made of commodity parts competes
directly with LiteX, which is loved and has 4,200 stars, and wins only on
being SV. The platform kit differs in what it generates: device behaviour
models that can't drift from the RTL, plus verification collateral. That is
the part LiteX, Chipyard and OpenTitan all write by hand.

## 3. What the kit is

```
             platform configuration (SV classes)
                          |
       +--------+---------+---------+------------+
       |        |         |         |            |
      RTL     model     device    headers      tests
    (top +   (QEMU /    tree      + docs     (fw-hdl-dv,
   devices)   Renode)                         checkers)
```

- **Devices are fw-hdl classes.** Each is configured at elaboration and has:
  - a transaction-level model that is register-accurate and functional, not
    cycle-accurate;
  - an RTL lowering.
- **The model reaches the emulator through fw-hdl's C view, not through a
  simulator.**
  - The model is compiled into a thin QEMU device or Renode peripheral
    wrapper.
  - Running the SV class model in a simulator and bridging to QEMU (DPI,
    remote-port) is the fallback. It is slower and needs a simulator licence.
  - This puts the C implementation of the fw-hdl spec on the critical path.
    Check its readiness first (§6).
- **The platform generator** walks the configuration and emits:
  - the RTL top;
  - a QEMU machine file or Renode `.repl`;
  - the device tree;
  - C headers;
  - documentation.
- **What gets wrapped:**
  - Cores: CVA6 or VexRiscv for Linux; Ibex or picorv32 for small
    configurations.
  - Interconnect: PULP axi or the fw-proto-axi crossbar.
  - Memory controllers: vendor IP or LiteDRAM on FPGA.
- **Every device ships with:**
  - fw-hdl-dv tests and bind-on checkers (the §4b observability kit);
  - formal properties on its bus and interrupt interfaces;
  - an RTL-only release package ("build with fw-hdl, ship plain SV").

## 4. How it ties to the rest of the strategy

- **It is the flagship (P1).** The flagship moves toward a Linux-capable
  RISC-V platform. The near-term Wishbone SoC stays as the stepping stone.
- **It shows mixed abstraction (P4) in its most useful form.** The same block
  runs as a QEMU model, in simulation and on an FPGA. The factory swaps model
  for RTL per device, which gives hybrid runs: model everything except the
  block under test.
- **It carries the observability vehicle (§4b).** The interfaces of every
  device are AXI-Lite plus interrupts, and the kit's monitors are already
  bound to them.
- **It feeds the testbed story.** The virtio and DMA engines are descriptor
  and ring engines, the same family as the traffic-generator demo. The
  virtqueue engine is shared work.
- **The freecores wrapping effort remains the on-ramp.** The 16550 rewrite
  becomes the pilot for one-source model generation (§5, step 1).

## 5. Sequence

| Step | Deliverable | What it proves | Exit test |
|---|---|---|---|
| 1. Pilot | `fw-uart16550`'s class model compiled into a QEMU device; a minimal RISC-V machine | The model and RTL come from one source | Linux console boots through the generated device on QEMU and on Verilator with the same image. Measure the code against QEMU's hand-written `serial.c` |
| 2. Interrupt kit | PLIC and ACLINT, then APLIC and IMSIC; configurable; formally checked | Value where open RTL is weakest | Upstream Linux AIA drivers work on QEMU (generated model), Verilator and FPGA; formal proofs published |
| 3. Platform generator v1 | Configuration to RTL top, QEMU machine or Renode `.repl`, device tree, headers | The platform frame | One configuration change, such as adding a UART or changing the hart count, propagates everywhere with no hand edits |
| 4. Virtio family | A shared virtqueue engine; console and rng, then blk and net | A new open category | Unmodified `virtio_mmio` drivers on QEMU `virt`-style and FPGA platforms |
| 5. IOMMU, staged | Bare translation, then two-stage, then MSI remapping into the IMSIC, then ATS | The high-value block | Cross-checked against the spec's C reference model and QEMU's model |
| Alongside | Interconnect: wrap PULP axi, or a modest crossbar generator on fw-proto-axi | — | — |

Step 1 is cheap and decides whether the rest is credible. Do it before
committing to the category.

## 6. Risks and what to check

1. **The C view must exist and be good enough.** The whole story depends on
   lowering the class model to a C model that QEMU and Renode can host.
   - The pitch names the C model as a peer implementation, but fw-hdl-sync
     has no C emitter today: `python/fw/hdl/emit/` holds SV and register-block
     emitters only. The likely route is a C lowering from Zuspec IR, not
     bespoke fw-hdl code.
   - If it is far off, the fallback is the simulator bridge. That fallback
     weakens "fast model" to "co-simulation", which already exists
     (Antmicro, Xilinx `libsystemctlm-soc`).
2. **Licensing.** QEMU is GPLv2, and Apache-2.0 is not compatible with GPLv2.
   - Generated QEMU device code needs a compatible licence: a BSD/MIT
     exception for generated code, or GPL for the wrapper only.
   - Decide before the pilot.
   - Taxi's dual CERN-OHL-S or commercial licence is a model to study for
     the IP itself.
3. **Upstream.** OpenTitan keeps a QEMU fork rather than upstreaming.
   - Plan for a fork, or for out-of-tree devices.
   - Renode's external-peripheral mechanism is the easier first target.
4. **Commoditization by the core vendors.** SiFive, Andes and others bundle
   AIA and the IOMMU with their cores.
   - The open buyers are RISC-V SoC teams that are *not* buying a vendor
     platform: CVA6 and OpenHW users, academia, FPGA SoCs, and server
     startups.
   - Check how many there are.
5. **Scope.** A Linux-capable platform is large.
   - Hold the line: write the platform devices and wrap everything else.
   - The IOMMU is staged, and stage 1 alone is useful.
6. **Competing with LiteX.** Differentiate on:
   - generated device models;
   - verification collateral;
   - readable SV output for ASIC flows.

   Not on board count. Consider interoperating: a LiteX SoC using fw-hdl
   devices.
7. **Interrupt and IOMMU semantics are subtle.** Formal properties plus the
   spec's reference model are the answer. They are also the selling point,
   since the open incumbents say "not formally verified".

**Interview targets:**
- lowRISC and Rivos (OpenTitan QEMU maintainers): what would generated
  models be worth to them?
- Antmicro (Renode): their model-writing costs, and who pays.
- Ventana and other RISC-V server teams: AIA and IOMMU sourcing.
- OpenHW and CVA6 users: what blocks Linux SoC bring-up.
- FPGA SoC builders: would they adopt an SV platform kit over LiteX?

## 7. Open decisions

- Accept the platform-kit focus and the interrupt-kit lead?
- Licence for generated emulator code.
- Emulator target first: Renode (easier integration, embedded audience) or
  QEMU (Linux and server audience, harder upstream).
- Core for the Linux configuration: CVA6 (OpenHW, ASIC-credible) or VexRiscv
  (FPGA-friendly, SpinalHDL output).
